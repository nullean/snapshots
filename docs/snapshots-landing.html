Small, strict, readable

A snapshot test is only as good as the moment you look at its failure. Everything here is built for that moment.

plain text
Messages people and agents can act on

No colour codes, repository-relative paths, at most 20 differences and 80 lines, and the exact command to accept.
structural
Compared as DOMs and trees

Attribute order, whitespace, key order and 1 versus 1.0 do not fail a test. A changed field is reported by its path.
never automatic
You accept, or nothing changes

No auto-accept, ever. SNAPSHOT_ACCEPT=1 works on your machine; in CI it is ignored and the failure says so.
tidy
One folder per project

Verified files under .snapshots/, mirroring your tests. Received files in obj/ or your artifacts folder, never in source.
native AOT
A CLI that starts instantly

snap reviews, accepts, rejects and finds orphaned snapshots, native on Linux, macOS and Windows.
lightweight
Trim- and AOT-safe throughout

No heavy core, and every write is scoped to the snapshot folders, so even a bug cannot touch anything else.

Seven formats

Text stored as UTF-8 with LF endings, images as given, each compared its own way.

FormatAssertionsCompared
TextMatchSnapshotline by line, shown as unified hunks
HTMLMatchHtmlSnapshot, BeHtml, ContainHtmlas a DOM with AngleSharp.Diffing; select, remove and transform first
JSONMatchJsonSnapshot, BeJsonas a tree: keys in any order, numbers by value, arrays aligned item by item
YAMLMatchYamlSnapshot, BeYamlas a tree with the YAML 1.2 core schema, stored as written, comments and all
ImagesMatchImageSnapshotby pixels, perceptually, with anti-aliasing left out and a diff image on failure
Browser journeysMatchJourneySnapshot, MatchAriaSnapshotagent-browser commands run in Chrome; each read compared as a tree
HTTPMatchHttpSnapshot, MatchHttpFileSnapshot.http files run in order; status, chosen headers and JSON bodies compared as trees, secrets redacted

Browser journeys

Click through a running site with Nullean.Cdp: a text file of agent-browser commands, run in Chrome with no Node and no daemon. Every read lands in one transcript per journey, compared as a tree, so a failure names the node that moved.

● ● ●journeys/shop.journey
# Search, add a lamp, look at the basket.
open index.html
find label Search fill lamp
find role button click --name Search --exact
snapshot -c -s "#results"
find role button click --name "Add red lamp"
get text #count
click "a[href='basket.html']"
get title
snapshot -c -s main
● ● ●ShopJourneys.cs
[Test]
[JourneyFiles("journeys")]   // a test case per file
public Task Run(SnapshotFile journey) =>
    JourneyTest.RunAsync(journey,
        new() { BaseUrl = server.Url });

Add a11y, links, network requests --failed or Web Vitals budgets and they snapshot too; screenshots and HAR files land next to the received transcript. Browser journeys →

HTTP APIs

Run the .http files you already keep for Visual Studio, Rider or the REST Client against any HttpClient, WebApplicationFactory's included. Each response is snapshotted: status, the headers you choose, and JSON bodies compared as trees.

● ● ●http/orders.http
### login
POST {{host}}/api/login
Content-Type: application/json

{"user": "ada"}

###
GET {{host}}/api/orders
Authorization: Bearer {{login.response.body.$.token}}

###
GET {{host}}/api/missing
● ● ●ApiTests.cs
[Test]
[HttpFiles("http")]
public Task Run(SnapshotFile file) =>
    HttpFileTest.RunAsync(file,
        new() { Client = factory.CreateClient() });

[Test]
public async Task Orders() =>
    await (await client.GetAsync("/api/orders"))
        .Should().MatchHttpSnapshot();

Secrets from user secrets, configuration or environment variables are redacted from everything written, even when a server echoes them back. snap http run runs the same files against a live host. HTTP →

Review, then accept

snap walks through what changed, one snapshot at a time. Accept it, reject it, or skip it for later. Keys can be given in full, as a unique suffix, or as a glob.
